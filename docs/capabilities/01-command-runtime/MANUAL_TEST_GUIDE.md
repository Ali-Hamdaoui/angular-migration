# G01 — Governed Command Runtime: Manual Test Guide

## 1. Purpose

This guide validates the G01 Governed Command Runtime — command registry and policy, authoritative execution evidence, live log streaming, and JobSupervisor cancellation. It covers S3-F01 through S3-F04 features.

What this guide validates:
- Command template inspection and policy validation (S3-F01)
- Command execution with authorization_decision_id, state-version protection, and runtime evidence (S3-F02)
- Log streaming with cursor-based reconnect (S3-F03)
- Process cancellation with cancel_event and lease management (S3-F04)
- Environment sanitization (no backend secrets leaked to subprocess)

What it does NOT validate:
- Cross-goal integration (requires G02–G05 merged branches)
- Full Angular fixture acceptance (requires Goal 10 harness)
- Long-running async SSE push (uses synchronous chunk append + polling)

## 6. Manual Test Cases

### MT-001 — S3-F01: Register structured commands and reject arbitrary shell execution

**Goal**: Verify operator can inspect approved command templates and see raw shell strings, forbidden flags, or invalid arguments rejected before execution.

**Preconditions**: Backend running on port 8301, database seeded with default templates.

**Commands or UI steps**:
1. List registered templates:
```bash
curl -s http://127.0.0.1:8301/api/v1/operator/command-templates | python3 -m json.tool
```
2. Validate a valid command (python --version):
```bash
curl -s -X POST http://127.0.0.1:8301/api/v1/operator/command-policy/validate \
  -H "Content-Type: application/json" \
  -d '{"command_id":"python-version","executable":"python","arguments":["--version"],"run_id":"test-run-1","idempotency_key":"mt001-val1"}' | python3 -m json.tool
```
3. Validate a rejected command (unknown command):
```bash
curl -s -X POST http://127.0.0.1:8301/api/v1/operator/command-policy/validate \
  -H "Content-Type: application/json" \
  -d '{"command_id":"unknown-cmd","executable":"malware","arguments":["--destroy"],"run_id":"test-run-1","idempotency_key":"mt001-rej1"}' | python3 -m json.tool
```

**Expected API behavior**:
- Step 2: `{"decision": "accepted", "authorization_id": "...", "reasons": []}`
- Step 3: `{"decision": "rejected", "reasons": ["command_id 'unknown-cmd' is not registered", ...]}`

**Expected UI behavior**: CommandPolicyInspector shows template list, validation button triggers policy check, decision shown with green/red indicator.

**Expected database state**: `command_authorization_audits` table has 2 rows (1 accepted, 1 rejected).

**Expected events**: COMMAND_AUTHORIZATION_ACCEPTED and COMMAND_AUTHORIZATION_REJECTED events emitted.

**Expected artifacts**: Sanitized command authorization decision artifact for operator tests.

**Evidence to capture**: curl response, DB query for audit records, event stream output.

**Pass criteria**: Accepted response for valid template, rejected response for unknown command, both with correct reasons.

**Failure interpretation**: If both succeed or both fail, policy engine is not correctly filtering.

### MT-002 — S3-F02: Execute one approved command and persist authoritative command evidence

**Goal**: Verify a user can run one harmless approved diagnostic command and inspect exact executable, argv, profile, exit code, and immutable stdout/stderr evidence.

**Preconditions**: S3-F01 passing, backend running, templates seeded.

**Commands or UI steps**:
1. Create a test run:
```bash
curl -s -X POST http://127.0.0.1:8301/api/v1/runs \
  -H "Content-Type: application/json" \
  -d '{"source_path":"/tmp/test-source","target_version":"21","idempotency_key":"mt002-run1"}' | python3 -m json.tool
```
2. Execute the accepted authorization (python --version). The authorization response supplies `authorization_id`; execution does not accept executable, arguments, working-directory, profile, or shell fields from the client:
```bash
curl -s -X POST http://127.0.0.1:8301/api/v1/runs/{run_id}/commands \
  -H "Content-Type: application/json" \
  -d '{"authorization_decision_id":"{authorization_id}","expected_state_version":{state_version},"idempotency_key":"mt002-exec1","requested_by":"operator"}' | python3 -m json.tool
```
3. Retrieve execution record:
```bash
curl -s http://127.0.0.1:8301/api/v1/runs/{run_id}/commands/{execution_id} | python3 -m json.tool
```

**Expected API behavior**:
- Step 2: Response is `202 Accepted` and includes `execution_id`, `status: "PENDING"` or `"RUNNING"`, `idempotent_replay: false`, and the authoritative command fields.
- Step 3: Record shows `status: "SUCCEEDED"`, `exit_code: 0`, `runtime_checksum: "sha256:..."`, `authorization_id: "..."`

**Expected UI behavior**: Command detail drawer shows exact command, lifecycle (queued → running → succeeded), evidence links.

**Expected database state**: `command_executions` has 1 row with status=SUCCEEDED, exit_code=0, runtime_checksum=sha256:...

**Expected events**: COMMAND_QUEUED → COMMAND_STARTED → COMMAND_SUCCEEDED

**Expected artifacts**: Command manifest, full stdout ("Python 3.11.15\n"), full stderr (empty).

**Evidence to capture**: curl responses, DB query for execution record, event sequence.

**Pass criteria**: Successful execution with correct checksum, exit code, and authorization trail.

#### Current authorization-bound request contract

The command policy step must complete first. The accepted decision is the only authority for executable, arguments, profile, workspace, shell mode, timeout, and environment. The execution endpoint reloads those values by `authorization_decision_id`; the client cannot redefine them. `expected_state_version` must equal the current run snapshot. A retry of the same logical request reuses the same idempotency key; a different logical request uses a new key.

Successful submission (`202 Accepted`):

```json
{
  "execution_id": "exec-001",
  "run_id": "run-001",
  "status": "PENDING",
  "idempotent_replay": false,
  "authorization_id": "auth-001",
  "state_version": 8,
  "event_sequence": 12
}
```

Stale state (`409`): `{"error_code":"STALE_STATE_VERSION","message":"The run state version is stale","details":{"expected":7,"actual":8}}`.

Idempotent replay (`202`): the same `execution_id` with `"idempotent_replay": true` when the key and authorization payload identify the same logical request.

Idempotency conflict (`409`): `{"error_code":"IDEMPOTENCY_KEY_CONFLICT","message":"The idempotency key was already used for a different request"}`.

Authorization rejection (`409` or `422`, depending on the rejection): `{"error_code":"AUTHORIZATION_STALE","message":"The authorization decision is not accepted for this run"}`. No process or execution artifacts are created.

Process failure (`202` submission, terminal `FAILED` on retrieval): the execution detail contains `status: "FAILED"`, `exit_code`, `failure_code`, and the registered artifact IDs for stdout, stderr, command manifest/log, and result report.

Artifact retrieval (`200`):

```text
GET /api/v1/artifacts/{artifact_id}
```

The response is backend-owned artifact content and metadata, including `artifact_id`, `artifact_type`, `checksum`, `relative_path`, and finalized status. Clients use the artifact ID only; absolute filesystem paths are never exposed.

### MT-003 — S3-F03: Stream live command logs and recover after browser reconnect

**Goal**: Verify user can tail stdout/stderr for a running command, pause the viewer, refresh, and resume from stored logs.

**Preconditions**: S3-F02 passing, backend running.

**Commands or UI steps**:
1. Execute a long-running command (Python loop printing output):
```bash
curl -s -X POST http://127.0.0.1:8301/api/v1/runs/{run_id}/commands \
  -H "Content-Type: application/json" \
  -d '{"authorization_decision_id":"{authorization_id_for_registered_log_fixture}","expected_state_version":{state_version},"idempotency_key":"mt003-exec1","requested_by":"operator"}' | python3 -m json.tool
```
2. Retrieve logs after completion:
```bash
curl -s "http://127.0.0.1:8301/api/v1/runs/{run_id}/commands/{execution_id}/logs" | python3 -m json.tool
```
3. Retrieve with cursor (simulate reconnect at sequence 2) via the SSE streaming endpoint:
```bash
curl -s "http://127.0.0.1:8301/api/v1/runs/{run_id}/commands/{execution_id}/logs/stream?cursor=2" | python3 -m json.tool
```
4. Filter by stream:
```bash
curl -s "http://127.0.0.1:8301/api/v1/runs/{run_id}/commands/{execution_id}/logs?stream=stdout" | python3 -m json.tool
```
5. Get stream summary:
```bash
curl -s "http://127.0.0.1:8301/api/v1/runs/{run_id}/commands/{execution_id}/logs/summary" | python3 -m json.tool
```

**Expected API behavior**:
- Step 2: All chunks returned with sequence numbers
- Step 3: Only chunks with sequence > 2 returned
- Step 4: Only stdout chunks returned
- Step 5: total_chunks and per-stream counts

**Expected UI behavior**: LogViewer shows live scrolling output, pause button freezes view, reconnect after refresh shows accumulated logs.

**Expected artifacts**: Full immutable stdout/stderr logs.

**Evidence to capture**: Log chunks with sequences, cursor filtering, stream filter results.

**Pass criteria**: All chunks retrievable, cursor filtering works, stream filters work.

### MT-004 — S3-F04: Own commands with JobSupervisor, leases, timeout, and explicit cancellation

**Goal**: Verify user can cancel a controlled long-running command and see graceful then forced process-tree termination.

**Preconditions**: S3-F02 and S3-F03 passing, backend running.

**Commands or UI steps**:
1. Execute a long-running command (sleep 30):
```bash
curl -s -X POST http://127.0.0.1:8301/api/v1/runs/{run_id}/commands \
  -H "Content-Type: application/json" \
  -d '{"authorization_decision_id":"{authorization_id_for_registered_cancellation_fixture}","expected_state_version":{state_version},"idempotency_key":"mt004-exec1","requested_by":"operator"}' | python3 -m json.tool
```
2. Check active command:
```bash
curl -s http://127.0.0.1:8301/api/v1/runs/{run_id}/active-command | python3 -m json.tool
```
3. Cancel the command:
```bash
curl -s -X POST http://127.0.0.1:8301/api/v1/runs/{run_id}/commands/{execution_id}/cancel \
  -H "Content-Type: application/json" \
  -d '{"actor":"operator","idempotency_key":"mt004-cancel1"}' | python3 -m json.tool
```
4. Verify cancelled state:
```bash
curl -s http://127.0.0.1:8301/api/v1/runs/{run_id}/commands/{execution_id} | python3 -m json.tool
```

**Expected API behavior**:
- Step 1: execution_id returned with status=RUNNING
- Step 2: active command returned with execution_id
- Step 3: {"cancelled": true, "execution_id": "..."}
- Step 4: status=CANCELLED, cancelled=true, cancel_requested_by="operator"

**Expected UI behavior**: Cancel button with confirmation dialog, cancelling status indicator, partial evidence links, blocked duplicate action.

**Expected database state**: `command_executions` row has `cancelled=true`, `cancel_requested_by="operator"`, `cancel_requested_at` set.

**Expected events**: COMMAND_QUEUED → COMMAND_STARTED → RUN_CANCEL_REQUESTED → COMMAND_CANCELLED

**Expected artifacts**: Partial logs, process-termination report.

**Evidence to capture**: Cancel response, execution record after cancel, event sequence.

**Pass criteria**: Cancel returns success, execution shows cancelled=true, process terminates.
